## Implications

### Why is ukf_accumulate so slow?

Looking at the code (ukf_helpers.py:102-151), ukf_accumulate has a **sequential loop** that cannot be easily parallelized:

```python
for j in range(len(f)):  # Loop over ALL states (e.g., 256)
    Chol, info = torch.linalg.cholesky_ex(Sig)  # Cholesky decomposition
    # ... generate 6 sigma points ...
    Xsigmas = torch.vstack(
        sum(((lse2(mu + delta * Chol[:, i], ffh),
              lse2(mu - delta * Chol[:, i], ffh))
             for i in range(n - 1)), tuple()) +
        (lse2(mu, ffh + delta * sb), lse2(mu, ffh - delta * sb))
    )
    # ... update mu and Sig ...
```

For each of 256 states:
- 1 Cholesky decomposition (~10μs)
- 6 lse2() calls (~0.5ms total)
- Matrix operations (~0.5ms)
- **Total: ~1.0-1.5ms per state**

Expected time: 256 states × 1.5ms = **384ms per batch**
Actual time: **298ms per batch** ✓ (close to theoretical!)

This is **fundamentally sequential** - each iteration depends on the updated `mu` and `Sig` from the previous iteration. This is the UKF update step.

### Why is lse2() so slow in aggregate?

lse2() is called **179,300 times** during training:
- 16.59s / 179,300 calls = **0.0925ms per call**

This is actually quite fast! The problem is the sheer volume of calls:
- 6 lse2() calls per state in ukf_accumulate
- 256 states per batch
- 100 batches
- = 153,600 calls just from ukf_accumulate

The lse2() function is already optimized (using torch.logsumexp), so not much room for improvement.

## Optimization Recommendations

### Priority 1: Optimize ukf_accumulate Sequential Loop (HARD)

**Current bottleneck: 29.84s (46% of time)**

Options:

1. **Parallel UKF variants** (research required)
   - Look for parallelizable UKF formulations
   - May sacrifice some accuracy
   - Potential speedup: 5-10x

2. **Batched operations using torch.vmap()**
   - Use PyTorch's vmap to batch Cholesky and lse2 calls
   - May not work due to sequential dependency
   - Potential speedup: 2-3x if feasible

3. **Custom CUDA kernel**
   - Write specialized CUDA kernel for this specific loop
   - Significant development effort
   - Potential speedup: 3-5x

4. **Dimensionality reduction**
   - Reduce from 256 states to fewer representative states
   - Trade accuracy for speed
   - Potential speedup: Linear with reduction factor

5. **Accept the tradeoff**
   - UKF sequential is inherently sequential
   - Consider using a different loss function for large buckets
   - Use UKF only for small-medium buckets (<100 states)

### Priority 2: Reduce lse2() Call Overhead (MEDIUM)

**Current overhead: 16.59s (25.6% of time)**

Options:

1. **Cache repeated lse2() calls**
   - Some calls might be repeated with same inputs
   - Profile to check if caching would help
   - Potential speedup: 10-20% if many duplicates

2. **JIT compilation**
   - Use torch.jit.script on lse2() and ukf_accumulate
   - May help PyTorch optimize better
   - Potential speedup: 10-30%

3. **Fused operations**
   - Combine multiple lse2 calls into single custom operation
   - Requires custom kernel
   - Potential speedup: 20-40%

### Priority 3: Use Different Loss for Large Buckets (EASY)

**Practical recommendation:**

For buckets with >100 states, switch to a faster loss function:
- logspace_mse_fdb: ~10x faster
- elp_least_squares: ~5x faster
- Only use ukf_sequential for critical small buckets

Implementation:
```python
if bucket_size > 100:
    config['loss_fn'] = 'logspace_mse_fdb'
else:
    config['loss_fn'] = 'ukf_sequential'
```

## Summary

**The UKF sequential loss is fundamentally limited by the sequential nature of ukf_accumulate.**

Current performance:
- 64.7 seconds for 100 epochs on a typical bucket
- 46% of time spent in ukf_accumulate (sequential loop)
- 26% of time spent in lse2 calls (mostly from ukf_accumulate)

The optimizations we've already implemented (vectorization, reduced sampling) are working well. The remaining bottleneck is architectural - the sequential UKF update loop cannot be easily parallelized without changing the algorithm itself.

**Recommended next steps:**
1. Accept the current performance for small-medium buckets (<100 states)
2. Use faster loss functions (logspace_mse_fdb, elp) for large buckets
3. Investigate torch.jit.script for modest 20-50% speedup
4. For significant speedup (5-10x), would need to research fundamentally different algorithms
