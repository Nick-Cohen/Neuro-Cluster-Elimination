## Shipped (code / method)
- **Backtracking merge** (`reduce_nn_merge`, config `reduce_nn_backtrack`): after finding the
  min NN count reachable within cap $D$, re-run at the *smallest* bound achieving it (binary
  search w/ snapshot/restore). Removes cluster bloat — e.g. rbm_22 D24 & D28 both collapse to
  the same maxElim-22 computation. (lab 2026-06-10) → [[merge-bound]], [[bucket-merging]].
- **OOM-safe exact streaming** (`stream_nn_exact`): `_compute_message_exact_chunked` evaluates
  NN factors per output-slice instead of densifying the full $2^{\text{scope}}$ grid; verified
  identical to `to_exact` to ~1.9e-6. (lab 2026-06-10) → [[codebase-map]].
- **Dynamic sample-gen memory budget** (`_dyn_streaming_budget`, `NCE_SAMPLE_MEM_FRAC`): size
  the streamed block from *free* GPU memory and the widest NN factor's per-row footprint;
  env block-size is now only an upper cap. Plus an internal chunk in `_eval_elim_block` as a
  hard OOM safety net. Both opt-in-free and result-identical. (lab 2026-06-12b)
- All changes default to prior behavior, so in-flight seed queues were unaffected.

## Experiments
- **435-run re-sweep launched** (lab 2026-06-10b): 29 problems × 5 merge-configs
  (no-merge; reduce-NN backtrack @ D=4/12/16; subsumption @ D=16) × 3 seeds. Two-phase
  `master_sweep.sh` (all 315 non-grid40 first, then 120 grid40), 4 GPU queues, 48h watchdog.
  Smoke test green (grid10x10 iB10: log_z 303.0858 vs ref 303.085957, abs_err 2e-4).
- Recovered 14 of 22 phase-1 failures after the memory fix; they coexist with grid40 phase 2.

## Findings
- **8 sweep "failures" are a real result, not a bug** (lab 2026-06-12b): high-cardinality
  pedigree (domain $k$=4–5) at [[merge-bound]] 16 needs exact training targets summing over
  $k^{16}$ terms ($5^{16}\approx1.5\times10^{11}$) — infeasible. A genuine limit of merge-16 on
  multi-valued problems; logged as gaps (`rerun_infeasible.txt`). → [[open-questions]].
- **Sample generation is launch-bound, not GPU-bound** at high $D$ (lab 2026-06-09): a D28
  cluster fires ~7M tiny kernels from one Python thread; GPU ~37% utilized. Corrected an
  earlier wrong "CPU-core contention" claim.
